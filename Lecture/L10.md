## Dynamic memory allocation 
* we have been statically initializing the size of an array at compile time
    * int arr[4]; --> the length 4 is defined at compile time (WILL ALWAYS HAVE 4 ELEMENTS)
* what if we want to create an array where the size is defined at *runtime*
```c
int len = 4;
char* darr = NULL;
darr = malloc(len * sizeof(char));

darr[8] = 'c'; // or *(darr + 8) = 'c'
```
* static arrays are fantastic 

## malloc() 
* standard c function in <stdlib.h>
* malloc creates or allocates an area of memory for you to store an array
* how do i input size? 
    * char pointer point to nothing
    * assign pointer to malloc(some length  * sizeof(char))
        * length of array
        * sizeof() bytes per element
* once you dynamically allocate memory it acts like any other array 
    * length is now a variable that you can control at runtime

### where are malloc() allocations in memory
* comes from the **heap** which grows from low addresses up
* everytime you call malloc() you allocate memory growing up, more calls, bigger the heap grows up
* **why do we split the memory in half?**
    * stack grows in a predictable way 
        * you know how much memory function needs when compile bc parameters are passed in the code
    * heap grows arbitrarily depending on what the function does *as its running*

* sizeof() returns number of bytes a data type needs
* if pass in a var thats a pointer it will say how many bytes needed to store a POINTER not whatever it is being pointed to 

#
* you do not always need to use malloc() when you need to store arrays
* in C when you dynamically allocate YOU have to deallocate the memory when you are done
* when you know the biggest size of the array, **PUT IT IN THE STACK NOT IN THE HEAP**
    * the compiler automatically makes room for them on the stack
* when you **don't know** the size of arrays at compile time, you need to allocate them from another memory of region
    * **heap**

## When is allocated memory available again to reuse for other allocations?
* Stack *(Static allocation)*: As soon as the function ends the variables are no longer considered used on the stack
     You do not need to do anything to free a variable on the stack
* Heap *(Dynamic allocation)*: The programmer must manually free(ptr) the allocation
     How can you guarantee that there is no other code that will use a pointer again?
        » Pointers can be copied as variables in functions, returned from functions, put into arrays.
     One of the hardest problems in computer science is automatically determining when it’s ok to free()
» Java/Python’s garbage collection, Rust’s ownership model
     If a pointer is no longer accessible, you may never be able to free it during the program!
        » This is called the dreaded: **“Memory Leak"**
        * free is a runtime issue
        * use after free errors: use memory that is freed
