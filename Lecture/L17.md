## Process: A running program on an OS
* fork() new entity/context created which captures everything needed to understand *that* new process that is running
    * includes any global variables
* when you run a program on an OS it starts a "process"
* a process is an abstraction provided by the OS of a single isolated running program 

### a process includes all of the **context** of the program
* memory: stack/heap and code
* registers: current state of a running process/execution (instruction in the code)
* peripherals: even disk access (external to the main processor but still related to the process)

* *advantage* --> processes are completely isolated form each other:
    * you **can NOT** overwrite another processes' stack/heap code

## Process State: What does an OS maintain?
* process ID (PID)- a unique number for a process
* the address space (range) in RAM for the process
    * remember the programs are actually in the virtual memory
* the execution state of the process (registers,...)
* the hardware resources in use (open files on disk)

* why is it useful to know where you are in a program? (we want to run multiple programs running at once) pausing a process to let other programs run, and then go back to resume that process 

## Context Switching: Changing processes
* we have code that takes struct of running process then loads info the struct to save that info *BEFORE* running the next program 

* **Context switching**: The Operating System decides when to switch between processes
    * one of the biggest benefits of the process abstraction 

* When an OS decides that a process had its time to execute it performs the context switch
    * OS saves all context of ONLY the running process by copying all Registers to RAM
    * The OS then copies the saved context of another process from RAM to the Registers
    * The new context switched process begins 

* a process starts in a ready state
    * a program may break or pause for a second --> *blocked state* 
        * like I/O, or when we run fgets()...wait for some sort of external event 
    * after a block is done, it goes back to ready state
* *exit state* is reached many different ways 
    * struct that is running current problem is deleted

## Creating and destroying processes 
* int fork(); Ask OS to create a new process running the current code
    * creates a new process (new state for address space, PID, registers, hardware)
    * starts with a copy of the same memory of the running process
        * process starts with a *copy* of the stack, heap, and code


```c
pid_t pid; 
pid = fork();
printf("pid = %d\n", pid);
```
## Waiting for a process to finish
* int waitpid(pid_t pid, int* wstatus, int options):
* parent cannot run until child finishes running, the parent is in a *blocked* state
* AKA "only by a parent process"
* NULL will wait for all children to finish
* gets the return code from the child process
    * WIFEXITED(wstatus) - check if child process has **exited**
    * WEXITSTATUS(wstatus) - get return status integer

## What if a parent does NOT wait for a process to finish?
* parent wants to know exit status/return value of the child even if it is terminated
* *zombie process*- child is no longer running but it also is still alive waiting for the parent to ask it

## Zombie processes
> "are you dead? if so, what is your return value?" -parent
* parent process may never get to it/check on it --> may be a zombie forever

# Review questions
1. 1. Does a running process always run instructions or does it ever stop? Why
would it stop?

    No, not always. A running programs may be go into a blocked state at any time 
    depending on how the OS's behaviour. For example, if a process needs to wait 
    for data from the hard drive, the OS may context switch to another process to 
    avoid wasting CPU time. 

2. What code runs that will copy the running process into a new running
process?

    fork()

3. If a parent has not yet wait()'ed for their child process but the child
terminates, should the parent still be able to wait for it? Why or why not?
    
    Yes, it should still be able to wait() for it. This is to guarantee that the 
    parent process can always find the child's exit status. If the OS deletes that
    information, then the parent would never know if the child succeeded or encountered
    some kind of error.
